# Зафиксировать окружение, упаковку и первую интеграцию

**Ответственный:** Егор / PM  
**Приоритет:** P0 · **Этап:** Первый запуск  
**Контрольная точка:** T0 + 4 часа. Это внутренний ориентир; T0 и официальный дедлайн подтверждает PM.

## Зачем это нужно

Твоя задача — сделать одинаково понятный запуск для команды и корректный архив для платформы. Внутренняя папка репозитория и содержимое сдаваемого ZIP могут различаться.

## С чего начать

Сразу уточнить у Ивана выбранный способ запуска; пока он проектирует агент, собрать материалы, окружение и способ упаковки.

## Пошаговое выполнение

1. **Зафиксировать старт и официальный дедлайн.** В README или журнале записать T0 по МСК. Официальный дедлайн проверить на платформе. В Issues заменить относительные ориентиры реальными ближайшими сроками после разговора с Иваном и Юрой.

2. **Согласовать одну инструкцию запуска.** Попросить разработчиков указать версию Python, установку зависимостей, имена переменных и две команды для task.md. Записать в docs/RUNBOOK.md. Значения API-ключей в документ не вставлять.

3. **Проверить окружение.** Подготовить Python 3.12 и выбранную командой изоляцию. Проверить установку и импорты актуальных зависимостей на целевой ОС; если делаете свой Dockerfile, явно назвать его локальным воспроизведением, а не официальным образом.

4. **Снять конкретные блокеры.** Проверить доступ к выданному API, идентификатор модели, основной/резервный адрес по актуальной инструкции, пути и доступность библиотек в воркерах. Вопрос mcp разобрать с Иваном до привязки решения к нему.

5. **Описать и автоматизировать упаковку.** Создать команду сборки отдельного каталога/архива. В его корне должны быть solution.py, актуальный requirements.txt и все требуемые .py. Разворачивание вложенных модулей требует исправления импортов и проверки.

6. **Проверить содержимое ZIP.** Распаковать в отдельную чистую папку и запустить оттуда. Проверить размер до 100 МБ, имена файлов и отсутствие ключей, CSV-датасетов, локальных моделей и кэшей.

7. **Подготовить наблюдение за ресурсами.** Согласовать с разработчиками лог общего времени и памяти, лимиты потоков и запас на финальное обучение. Для одной задачи доступно 8 CPU и 32 GB; GPU отсутствует.

8. **Назначить раннюю интеграцию.** Собрать Ивана и Юру к первой общей команде не позже T0+8 ч. Зафиксировать 1–3 конкретных блокера вместо накопления больших несоединённых веток.

## Минимум для первой версии

Команда запуска и упаковки, проверенные зависимости и ранняя интеграция. Сложная инфраструктура в минимальную сдачу не входит.

## Готово, когда

- [ ] Документированы запуск и упаковка; команда может повторить их.
- [ ] Проверены ограничения 8 CPU / 32 GB RAM, отсутствие GPU и 30 GB диска; готовый образ организаторы не предоставляют.
- [ ] Назначена первая интеграционная сверка не позже T0 + 8 часов; собирать части начинаем до завершения всех улучшений.

## Как проверить

1. Другой участник может повторить RUNBOOK без устных дополнений.
2. Из распакованного ZIP доступны все нужные импорты; случайных ссылок на локальные папки разработчика нет.
3. Архив меньше лимита и содержит только предназначенные для платформы файлы.

## Что и кому передать

Ивану/Юре: RUNBOOK, проблемы окружения и команда сборки. В #10: проверенный способ получения релизного архива.

К передаче приложить: ссылку на коммит/PR или отчёт, точную команду проверки, фактический результат и оставшиеся ограничения. Слова «агент написал» сами по себе не подтверждают готовность.

## Типичные ошибки

- Передать архив с кодом внутри одной вложенной папки.
- Считать, что работающий локальный запуск автоматически доказывает совместимость с платформой.

## Если используешь агента

Скопировать в его рабочий чат этот Issue целиком и добавить:

> Работаем над автономным ML-агентом для хакатона. Выполни задачу #7 в пределах её ответственности. Сначала прочитай README.md, AGENTS.md и материалы карточки, проверь доступность входных файлов. Перед передачей выполни уместную проверку, приведи команду, фактический результат и известные ограничения. Если есть блокер, опиши его и продолжай независимую полезную часть работы.

Ответственный участник просматривает изменения и проверяет результат перед передачей. Секреты и крупные данные в Issue не прикладывать.
