# Собрать управляющего LLM-агента и вызов инструментов

**Ответственный:** Иван  
**Приоритет:** P0 · **Этап:** Первый запуск  
**Контрольная точка:** T0 + 8 часов. Это внутренний ориентир; T0 и официальный дедлайн подтверждает PM.

## Зачем это нужно

Это управляющая часть решения. LLM читает условие и результаты инструментов, затем решает, что запускать дальше. Готовые ML-инструменты разрешены; произвольная генерация кода не является обязательной.

## С чего начать

Разработать независимый цикл со временным инструментом, затем подключить реальные функции Юры. Сигнатуры взять из #1.

Согласования: [#1](https://github.com/selecteg12/alfa-automl-hackathon/issues/1). Прототип и изучение материалов можно готовить параллельно.

## Пошаговое выполнение

1. **Определить состояние агента.** Хранить описание задачи, профиль данных, доступные инструменты, историю экспериментов, лучший результат и оставшееся время. Не отправлять целые CSV в LLM.

2. **Настроить подключение.** Использовать предоставленные окружением адрес, ключ и идентификатор модели. Проверить короткий запрос. Значения секретов не помещать в код или отчёт; при проблеме записывать тип ошибки.

3. **Описать инструменты.** Сделать ясные входные схемы для профиля данных, обучения/оценки, предсказаний и сохранения ответа. Перед выполнением проверять аргументы и поддержку выбранной конфигурации.

4. **Получить первое решение LLM.** Передать задачу и компактный профиль. Модель должна объяснить выбранный тип задачи, метрику, подход и следующий вызов инструмента. Разрешённый фиксированный набор инструментов достаточен.

5. **Исполнить инструмент и вернуть результат.** Выполнить выбранное действие; передать LLM измеренную метрику, время и ошибки. Следующее действие должно зависеть от этих результатов, а не от заранее записанного номера шага.

6. **Обработать неудачные ответы.** Проверять наличие choices, содержимое ответа и аргументы. Делать ограниченные повторы для временных ошибок; сокращать слишком длинный контекст. Учитывать остаток общего времени.

7. **Зафиксировать завершение.** Агент выбирает лучший завершённый результат и вызывает финальное предсказание/запись через #6. Проверять существование корректного файла до успешного завершения.

8. **Показать настоящую агентность.** На двух запусках сохранить краткий журнал решений: что LLM выбрала, что выполнено, какую обратную связь получила и почему остановилась.

## Минимум для первой версии

Один агент управляет готовыми инструментами на двух публичных задачах; его решения видны в фактическом выполнении.

## Готово, когда

- [ ] В логах видно, какое решение приняла LLM и какой инструмент был реально вызван.
- [ ] При запуске на второй задаче не требуется ручная смена таргета или метрики.
- [ ] Сбой запроса не удаляет уже сохранённый результат и не вызывает бесконечные повторы.

## Как проверить

1. Замена результата инструмента влияет на следующее решение, а не только на текстовый комментарий LLM.
2. Пустой ответ, ошибка API и невалидные аргументы обработаны без бесконечного цикла.
3. Используется выданная модель; ключи отсутствуют в журнале.

## Что и кому передать

Юре: готовая точка вызова инструментов. Для #5: состояние и журнал, на которых строится исследовательский цикл. PM: команда запуска и перечень нужных переменных без значений.

К передаче приложить: ссылку на коммит/PR или отчёт, точную команду проверки, фактический результат и оставшиеся ограничения. Слова «агент написал» сами по себе не подтверждают готовность.

## Типичные ошибки

- Вызывать LLM для формальности, когда все действия всё равно жёстко предопределены.
- Потратить время на сложную мультиагентную архитектуру до первого рабочего прохода.
