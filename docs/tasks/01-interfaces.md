# Согласовать интерфейсы и правила чтения новой задачи

**Ответственный:** Иван  
**Приоритет:** P0 · **Этап:** Первый запуск  
**Контрольная точка:** T0 + 2 часа. Это внутренний ориентир; T0 и официальный дедлайн подтверждает PM.

## Зачем это нужно

Это общий язык между агентом Ивана и ML-инструментами Юры. После согласования Юра должен понимать, что принимает его функция и что она возвращает, а агент — как запустить эксперимент и прочитать результат.

## С чего начать

Начать первым и провести короткую сверку с Юрой. Согласовать минимальный контракт примерно за час; затем дополнять его без остановки разработки.

## Пошаговое выполнение

1. **Разобрать два реальных примера.** Открыть оба task.md. Выписать таблицу: тип задачи, пути файлов, целевые колонки, идентификатор, метрика, направление улучшения и требуемый ответ. Для публичных задач ответы известны; в рабочем коде эти сведения должны приходить из входных материалов.

2. **Определить описание задачи.** Предложить TaskSpec или аналог: путь к task.md, пути данных, task_type, target_columns, id_columns, metric, maximize/minimize и output_schema. Имена и формат структур выбрать вместе с Юрой; приведённые названия — ориентир.

3. **Отделить сведения от предположений.** Для каждого решения полезно сохранять источник: текст задачи, словарь, sample_submission или проверка CSV. Если сведений недостаточно, агент должен проверить данные и отметить неопределённость.

4. **Согласовать вызов эксперимента.** Определить, как передавать описание задачи, конфигурацию модели, разбиение, seed и оставшийся бюджет. В результате нужны score, имя метрики, направление, длительность, ошибка и ссылка на модель/предсказания.

5. **Согласовать проверку качества.** С Юрой выбрать начальное разбиение для каждой задачи. Для классификации рассмотреть стратификацию; для регрессии изучить контекст. id здесь не подтверждён как идентификатор здания, а Year_Factor — код периода.

6. **Проверить контракт без готового обучения.** Подставить два маленьких примера результата эксперимента и убедиться, что агент одинаково понимает «меньше RMSE лучше» и «больше Macro F1 лучше».

7. **Зафиксировать и передать.** Записать соглашения в docs/INTERFACES.md и добавить минимальные структуры или примеры в код. Отправить Юре ссылку на коммит и подтвердить, что его инструменты смогут реализовать этот интерфейс.

## Минимум для первой версии

Описания обеих публичных задач и единый вызов эксперимента. На этом этапе не требуется проектировать большой фреймворк.

## Готово, когда

- [ ] Иван и Юра используют одинаковые поля и соглашения.
- [ ] Есть примеры описания регрессии и классификации; формат допускает несколько целевых колонок и вероятности.
- [ ] Названия site_eui, attack_cat и id не зашиты как обязательные для любой задачи.

## Как проверить

1. Описание второй задачи загружается без изменения имён в коде.
2. Сравнение двух RMSE выбирает меньшее, двух Macro F1 — большее.
3. Есть явное представление схемы ответа; дополнительные выходные колонки не теряются по умолчанию.

## Что и кому передать

Юре: docs/INTERFACES.md, примеры входа/выхода, договорённость о разбиении. PM: список открытых вопросов и что может разрабатываться параллельно.

К передаче приложить: ссылку на коммит/PR или отчёт, точную команду проверки, фактический результат и оставшиеся ограничения. Слова «агент написал» сами по себе не подтверждают готовность.

## Типичные ошибки

- Выводить тип задачи только по числовому dtype таргета: код класса тоже может быть числом.
- Смешивать таблицу примеров публичных задач с обязательными константами для private.

## Если используешь агента

Скопировать в его рабочий чат этот Issue целиком и добавить:

> Работаем над автономным ML-агентом для хакатона. Выполни задачу #1 в пределах её ответственности. Сначала прочитай README.md, AGENTS.md и материалы карточки, проверь доступность входных файлов. Предложенные имена будущих структур и файлов уточни по реальному коду и договорённости с Иваном. Используй разрешённые зависимости и ограничения платформы. Перед передачей выполни уместную проверку, приведи команду, фактический результат и известные ограничения. Если есть блокер, опиши его и продолжай независимую полезную часть работы.

Ответственный участник просматривает изменения и проверяет результат перед передачей. Секреты и крупные данные в Issue не прикладывать.
