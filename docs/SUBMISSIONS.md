## Порядок отправки

Проверено 23.10.2026 в [кабинете онлайн-тура](https://changellenge.com/personal/championships/stage/927270/).

1. Собрать ZIP **до 100 МБ**. В корне — `solution.py`, предоставленный `requirements.txt` и нужные `.py`. Подпись загрузчика «128 МБ» — технический порог; лимит нашего трека остаётся 100 МБ. Вложенные папки, конфиги, данные, модели и `.whl` не копируются; свой `pip` из решения недоступен.
2. Проверить одну версию ZIP на обеих публичных задачах. В каждый отдельный чистый каталог задачи перенести только корневые `.py` и requirements из ZIP, расположить данные по условию. Из этого каталога выполнить **`python3 solution.py task.md`**, как на платформе. `submission.csv` должен появиться рядом с `task.md`; старого ответа перед проверкой быть не должно. Проверить импорты без исходного репозитория. Во время выполнения разрешены промежуточные подкаталоги и `/tmp`.
3. Открыть «Загрузить решение», проверить остаток попыток, выбрать ZIP и подтвердить отправку появившейся кнопкой формы. Для AutoML загружается ZIP, даже если общая ошибка загрузчика упоминает CSV. Фактическое прохождение загрузки проверить в «Истории решений»; записать SHA, хеш/имя архива, время МСК и статус.
4. Статус **«Решение находится на проверке» означает очередь**. Завершение подтверждается сообщением **«Точность вычисления: …»** с оценкой либо ошибкой. Обе стадии различать в журнале; не расходовать новую попытку только из-за ожидания.
5. При ошибке сохранить её текст/скриншот и время отправки. Ошибки кода/формата передать разработчику; при повторяющемся сбое загрузки/скоринга обратиться к организаторам. Подробные технические логи могут быть доступны только администраторам. Не предполагать, что неудачная отправка не расходует попытку: проверить остаток в кабинете.

На момент проверки история решений пуста, оставалось три попытки. Это снимок состояния, а не счётчик на момент следующей отправки. Состав ZIP и интерфейс подтверждены кабинетом; правило выбора private-версии и два запроса деталей в сутки взяты из FAQ организаторов.

## Как выбирается версия для private

Платформа автоматически выбирает сохранённую отправку с **лучшим public score**. При одинаковом точном лучшем результате выбирается последняя такая отправка; отображаемый округлённый score может скрывать различие. Последний загруженный архив с меньшим score не заменяет лучший для private. Отзыв старой отправки по умолчанию не предусмотрен; конкретный случай решается с организаторами (FAQ 40–41, 46).

Поэтому с первой отправки проверяются настоящая агентная логика, ограничения и способность прочитать новую задачу. Статический ML-pipeline с неработающими вызовами LLM не подходит как допустимый кандидат. В первой версии достаточно минимального анализа результата и обоснованной остановки; фиксированного числа итераций нет.

В журнале для каждой отправки сохраняются SHA/архив/точный доступный score/статус и её ограничения для private. Перед финалом сверяется не только новый ZIP, но и текущий лучший сохранённый кандидат.
