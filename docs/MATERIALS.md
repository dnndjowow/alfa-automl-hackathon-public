## Обязательные ограничения

- Python 3.12; 8 CPU и 32 GB RAM отдельно на каждую задачу; GPU нет; диск 30 GB.
- На одну задачу до 3 часов от начала запуска. Файл ответа должен быть сохранён до остановки процесса.
- ZIP не больше 100 МБ. Платформа копирует только .py-файлы из корня ZIP и requirements.txt. Вложенные модули для сдачи недоступны.
- solution.py — точка входа. Интерфейс запуска и переменные окружения проверяются по baseline и входному task.md.
- Итоговый файл submission.csv сохраняется рядом с task.md. Требуемые колонки и вид предсказаний брать из материалов конкретной задачи.
- CSV не обязаны лежать в корне текущего каталога. Пути определять по описанию.
- Использовать предоставленные OPENAI_BASE_URL и OPENAI_API_KEY; идентификатор модели определять по контракту окружения, исходный baseline использует OPENAI_MODEL.
- Использовать только согласованные библиотеки. Актуальная копия списка — reference/requirements.txt. Не устанавливать пакеты из кода решения.
- Только выданная LLM через предоставленный API. Произвольного доступа в интернет в контейнере нет.
- Обучать на предоставленных данных; предобученные модели запрещены.

## Что уточняет FAQ

- Генерация кода LLM необязательна. Можно управлять готовыми инструментами; решения LLM должны реально влиять на действия.
- Один агент и несколько агентов оцениваются одинаково. Минимального числа исследовательских итераций нет.
- На private возможны разные табличные постановки, включая мультитаргет и ранжирование; обучение с учителем и одна целевая колонка не гарантируются.
- Возможны вероятности и несколько колонок ответа; единый формат Data Dictionary не гарантирован.
- Агент самостоятельно выбирает схему валидации по контексту задачи.
- NLP, компьютерное зрение и рекомендательные системы исключены. Отдельная поддержка изображений, аудио и видео не нужна.
- На автоматической проверке денежного и токенного лимита API нет. На разработке действует общий бюджет команды.
- Каждый запуск чистый. На каждой private-задаче обычно один запуск; лучшие решения могут проверить вручную.
- При одинаковом лучшем public score выбирается последняя такая отправка. Отображаемый score округлён.
- Готовый Docker-образ организаторы не предоставляют.

## Проверка перед сабмитом

Приоритеты уточнены [аудитом плана](PLAN_AUDIT.md): главный критерий — private score. Готовые ML-инструменты разрешены, генерация кода необязательна (FAQ 3–7). Дополнительные отчёты/описание архитектуры/история запросов не требуются для автоматической оценки (FAQ 8, 27); минимальное состояние нужно самому агенту для выбора лучшего результата. Итог не зависит от количества агентов/инструментов (FAQ 2, 48).

- Архив проверен на размер, корневые файлы и отсутствие секретов.
- Команда запуска повторяется; импорты работают в основном и дочерних процессах.
- Есть обработка таймаутов, пустых/обрезанных ответов LLM и невалидных параметров.
- Уже сохранённый результат переживает ошибку очередного эксперимента.
- submission.csv существует, не пуст, соответствует ожидаемым строкам и колонкам.
- Оставлен запас времени на финальное обучение и запись результата.
- Версия кода и архив записаны в журнал отправок.

## Что требует дополнительной проверки

1. В baseline есть импорт mcp, а в опубликованном requirements его нет. Проверить фактический контракт и доступность пакета; не добавлять зависимость без согласования.
2. В PDF встречаются названия solution.py и script.py; точку входа и фактическую команду сверить до первого сабмита.
3. Команда задала старт 23.10.2026 20:00 и финальное решение 25.10.2026 20:00 МСК. [График](EXECUTION_ORDER.md) построен по этим датам; PM сверяет дату на платформе при первом сабмите.
4. Дневной бюджет разработки — 600 ₽ на общий ключ. В инструкции по ключам указано обновление в 03:00 МСК; сверить актуальную инструкцию перед использованием.
5. Сабмиты: три в сутки, обновление в 00:00 МСК. Запросы деталей запуска: два в сутки; подробные логи не гарантируются.
