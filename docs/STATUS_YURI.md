### Иван, 25.10 02:10: просьба к ядру (одна строка, до 09:00)

**`ml_validation.row_groups`** использует как номер группы хэш всех столбцов X. В `GroupKFold` и `StratifiedGroupKFold` номера групп определяют, в какой фолд попадёт группа. Если добавить признаки, хэши меняются, и фолды перемешиваются, хотя сами группы прежние.

Воспроизведение: 15% полных копий строк, схема `group`, к X добавлены 3 признака. В регрессии фолд сменили 81% строк, в бинарной задаче — 21%.

Из-за этого `add_features` («сравнение на тех же фолдах») и сравнение запусков с разными наборами признаков на group-схеме на деле идут на разных фолдах. Публичная многоклассовая задача как раз на group.

Предлагаемое исправление, проверено: после него фолды совпадают на 100%.

```python
def row_groups(X):
    return pd.factorize(pd.util.hash_pandas_object(X, index=False))[0]
```

`factorize` нумерует группы по первому вхождению строки, поэтому номера не зависят от значений хэша и от добавленных столбцов.

Остальные находки ревью агента исправлены у меня в `39f4bb7`:

- выбор лучшего запуска при 3 временных фолдах;
- смесь при нескольких таргетах;
- кэш метрик по фолдам;
- откат `__row_order__`.

1. **Ранговая нормализация сдвинутых признаков** (ядро, Mac, ~30 мин). Каждое значение сдвинутого признака заменяется его рангом **внутри своего файла** (train отдельно, test отдельно): «высокий счётчик» тогда значит одно и то же при разных шкалах. 2. **Псевдоразметка test** (ядро или агент, Mac, ~40 мин). Обучаем → предсказываем test → строки test с очень высокой уверенностью добавляем в обучение с предсказанными метками → переобучаем.
