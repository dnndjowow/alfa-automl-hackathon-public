## F01 [P1]. Утечка таргета при group `target_mean` и распад групп

**Механизм — две части:**

1. **Утечка.** Для group-схемы `_te_scheme` возвращает `{}`, и `target_mean` считается по случайным 5 фолдам. Копии одной строки (одна group-часть валидации) попадают в разные случайные фолды и видят таргеты друг друга. Валидационная строка получает в признак таргеты строк своей же валидационной части.
2. **Распад групп.** Ядро определяет группы по `row_groups(X)` уже *с новыми признаками*. У копий одной строки `target_mean` и `__n` теперь разные (каждая исключает свой фолд), поэтому одна группа распадается на несколько. Группы и фолды меняются, а `plan_key` прежний, и `add_features` сравнивает кандидата с базой «как на тех же фолдах». На деле фолды другие, и копии одной строки оказываются по разные стороны train/valid.

**Воспроизведение** (из ревью): 10 групп по 10 одинаковых строк, fold 0 `GroupKFold`, меняем только `y[valid] += 1000` и пересчитываем признак:

| Что | Значение |
| --- | --- |
| изменение `target_mean` у валидационных строк | **1000** у всех 20 (без доступа к `y[valid]` это невозможно) |
| групп по X до / после добавления признака | **10 → 45** |
| валидация fold 0 до и после совпадает | **нет** |

**Связанный остаточный риск:** при смене плана (forward → backward) сохранённые ранее `target_mean`-признаки не пересчитываются. Изменение только `y` новой валидационной части меняет признаки её train на 333.33. `_reval_oof` и `tool_evaluate(validation=...)` тоже используют готовые признаки.

**Почему твой замер на Wine этому не противоречит:** скрытые ответы показывают, что признак со случайными фолдами помогает *модели на test*. Но CV, по которому `add_features` решает «принять или нет», при этом завышен. На другой задаче это даст ложное принятие.

**Последствия:** завышенный CV, ложное принятие признаков, неверное ранжирование запусков и смеси на group-задачах. Public-мультикласс как раз group, и private-мультикласс, скорее всего, тоже.

**Что предлагаю:**

- **Самое простое до исправления:** при group-схеме не строить `target_mean` (`_te_scheme` → отказ с заметкой). На public-мультиклассе `tcprtt` и так отклонялся CV, так что потери там нет.
- **Правильное исправление:** группы и фолды фиксируются один раз по *исходным* признакам, а таргетные статистики строки валидационной части считаются только по train её части (как ты сделал для temporal). При смене плана или сида признаки пересчитываются.
- **Ядро может помочь (предложение, только с твоего согласия):** `make_splits` примет готовые группы из плана (`plan["groups"]` — массив по строкам train). Тогда ты один раз считаешь `ml_validation.row_groups(X_исходный)`, кладёшь в план, и добавленные признаки больше не меняют группы. Изменение маленькое и обратно совместимое: без `groups` всё как сейчас. Если согласен — напиши здесь, сделаю отдельным коммитом с тестом.

## F06 [P2]. F1 второго бинарного таргета по positive-коду первого

- **Механизм:** positive-класс хранится для каждого таргета отдельно, но замыкание `_binary_metric` создаётся по кодеку только первого. Если у второго таргета код positive-класса другой, считается F1 противоположного класса.
- **Воспроизведение:** первый `y` — классы 0/1 (positive = 1, код 1), второй `risk` — bad/good (positive = bad, код 0). Для второго прогноз всегда good. `set_task` проходит. `_oof_metric('risk', …)` = **0.889**, а правильный F1 класса bad = **0.0**.
- **Последствия:** неверная метрика, выбор моделей и порогов для второго таргета.
- **Исправление:** создавать метрику для каждого таргета по его positive-коду.

## F07 [P2]. Колонки вероятностей нескольких таргетов копируются из шаблона

- **Механизм:** `class_map` разрешается только при `len(predictions) == 1` (`:1684`), остальные колонки берутся из `sample_submission` (`:1733–1735`).
- **Воспроизведение:** бинарные таргеты `y`, `z`, шаблон `id,y_0,y_1,z_0,z_1`, metric logloss, prediction_format proba. `set_task` проходит. В `_assemble` переданы по 120 разных вероятностей на таргет. **У всех четырёх колонок ответа `nunique = 1`** (0.5 из шаблона), notes подтверждают 4 копирования.
- **Последствия:** CSV правильный по форме, но обе обученные модели проигнорированы, и признаков ошибки нет.
- **Исправление:** отображение (таргет, класс) → колонка или явный отказ вместо копирования шаблона.

## F12 [P2]. Ошибочный temporal-запрос оставляет `__row_order__`

- **Механизм:** `_plan_from` добавляет `row_order` до проверки `direction`; при ошибке или нехватке бюджета `tool_evaluate` возвращается раньше отката.
- **Воспроизведение:** после `set_task` на kfold вызываем `evaluate` с `validation={strategy: 'temporal', column: 'row_order', direction: 'bad'}`. Ответ `ok: false`, но featureset **0 → 1**, `__row_order__` остаётся в X, схема по-прежнему kfold.
- **Последствия:** неудачный вызов LLM меняет дальнейшее обучение. Новый признак может ещё и разорвать группы дубликатов (как в F01).
- **Исправление:** проверять аргументы до изменения данных или делать общий откат (`finally`).

## F19 [P3]. Оценщик внешних задач падает на неполном CSV

- **Механизм:** `score` добавляет сообщение о неверной длине, но потом сравнивает массивы id разной длины.
- **Воспроизведение:** truth и sample — 3 строки (id 1, 2, 3), submission — 2 строки (id 1, 2) → `ValueError: operands could not be broadcast together with shapes (2,) (3,)`. Серия `run` прерывается вместо записи ошибки по этой задаче.
- **Исправление:** при неверной длине возвращать problems до сравнения id.
