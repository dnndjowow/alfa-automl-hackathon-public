## 1. Утечка внутри валидационного блока при временной схеме по датам

**Где.** `_target_mean`, ветка `times`, в сочетании с `ml_validation._temporal`.

**Механизм.**
- Ядро при ≤50 значениях времени делает часть из одного значения (года). При >50 значениях (даты, `__row_order__`) оно делит время на блоки по квантилям, и train части — строки *до начала блока*.
- `_target_mean` даёт строке среднее по всем строго более ранним строкам той же сущности. Внутри блока это и строки самого блока: модель этой части их не видит, а у test соседей с ответами нет.
- Итог: на валидации признак информативнее, чем будет на test. CV с признаком завышен, и `add_features` может принять признак, который на test даёт меньше.

**Воспроизведение** (синтетика: 4000 строк, 50 сущностей, даты на отрезке 0–1000, таргет сущности дрейфует во времени; временная схема ядра, 3 блока):

| Блок | R² признака на валидации, как сейчас | R² только по train этой части (так видит test) |
| --- | --- | --- |
| t ∈ [396, 591] | 0.685 | 0.550 |
| t ∈ [592, 799] | 0.680 | 0.589 |
| t ∈ [799, 1000] | 0.700 | 0.629 |

Если поменять таргеты строк блока, признак у последних строк блока меняется в 100% случаев.

**Не затронуто: годы и месяцы (≤50 значений), в том числе public-регрессия.** Там блок = одно значение, а строки того же периода ты исключаешь. Я поменял все таргеты валидационной части — её признак изменился на 0 (порядка 1e-15) и при `forward`, и при `backward`.

**Исправление (проверено на той же синтетике).** Для строк каждой валидационной части статистика считается только по train этой части. Для остальных строк (самые ранние периоды, ни в одну часть не попали) — как сейчас, «строго раньше».

```python
def _fold_safe(keys, values, splits, current):
    """current — признак «строго раньше» (как сейчас); строки валидационных частей — по train своей части."""
    out = np.asarray(current, dtype=float).copy()
    for train, valid in splits:
        stat = values.iloc[train].groupby(keys.iloc[train].values).mean()
        out[valid] = keys.iloc[valid].map(stat).values
    return out
```

- В `_te_scheme` для temporal добавить `"splits": ml_validation.make_splits(plan, split.X_train)`, а в ветке `times` применить `_fold_safe` к каждому `train_part`. Для `__n` — то же, но вместо `mean` взять `size`.
- Результат проверки:
  - **даты:** признак валидационных строк больше не зависит от их таргетов (изменение 0.0); вне валидации совпадает с текущим;
  - **годы:** признак совпадает с текущим **целиком**, то есть для public-регрессии ничего не меняется.

## 2. Ответы на твои вопросы

- **`direction="backward"` ты понимаешь верно.** Test раньше train. Умножение времени на −1 делает «прошлым» более поздние периоды, а test видит весь train, который весь позже него. Это совпадает с ядром: по значениям `train = values > v`, по блокам `train = values >= high`. Утечки нет (проверено, см. п. 1).
- **NaN во временном столбце:**
  - у таких строк признак NaN, в «прошлое» других строк они не входят;
  - в ядре они не попадают ни в одну часть temporal (ни в train, ни в valid), но участвуют в финальном обучении; признак у них NaN — это безопасно;
  - test видит среднее по всему train вместе с ними;
  - мелочь: счётчик `__n` у test считает и строки с NaN-временем, у train — нет.

## 3. group-схема на случайных фолдах

**Теория.** Если ключ почти совпадает с полной строкой, признак валидационной строки берёт таргеты её копий из той же group-части. CV тогда завышен.

**На public-мультиклассе разница мала.** `entity_keys` = `['tcprtt']`, `['tcprtt', 'synack']`:

| Ключ | Признак есть: случайные фолды | фолды group-схемы | test |
| --- | --- | --- | --- |
| `tcprtt` | 74.8% | 73.3% | 67.9% |
| `tcprtt` + `synack` | 67.0% | 65.4% | 57.6% |

Средняя |признак − факт класса|: 0.103 (случайные) против 0.105 (group). Твой выбор по Wine не оспариваю. Риск остаётся только для задач, где ключ ≈ полная строка.

## 4. `entity_keys` на мультиклассе

Берёт `tcprtt` — непрерывный замер задержки (RTT), а не сущность. Попаданий в test ≥ 0.6 только потому, что там много нулей. Это ложное срабатывание эвристики, но CV-ворота от него защищают. Цена — время одной проверки `add_features`.

## 5. Время fallback на крупных мультиклассах

- В `improve` теперь два CatBoost («вторая модель» и «портфель, catboost») плюс XGBoost `max_depth` 11 при `len(y) >= 5000`.
- Проверка перед шагом смотрит на длительность *предыдущего* шага (`reserve + 2 * last`), а перед CatBoost идёт быстрый LightGBM.
- Каждый `evaluate` ограничен `min(1800, left/3)` с, так что он не упадёт. Но на public-мультиклассе CatBoost занимает 35–48 мин на цикл (наш PC, `PC_RESULTS_3`). Два CatBoost могут съесть около часа и закончиться остановкой по времени с недообученной моделью.
- Это стоит посмотреть в репетиции (твой пункт 2). Возможная защита: пропускать «портфель, catboost», если первый CatBoost шёл дольше N минут или был остановлен по времени.
